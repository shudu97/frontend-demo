Agent Introduction

Animation
On the slide
  • "An agent is an application that completes a task by planning its own steps and calling tools that read files, run commands, or edit code." (source)
  • An agent is a model running in a loop: decide the next step, call a tool, read the result, decide again, until the task is done

Visual: A video.

To explain
  • The model
    • It makes the decision in each turn
    • We do not host any model; we connect to the Model API through Lumina Gateway, the Enterprise model access layer
    • It is currently Claude Sonnet. The version may change over time, so the slide names only the model family.
  • Core Tools
    • Skill, Bash, Read, Edit and Write are used in RiskMind. Glob, Grep and Agent are available but not used.
    • All Core Tools come from the Claude Agent SDK. RiskMind has no custom tools of its own.
    • Skill is itself a Core Tool: it is how an agent loads a skill (explained in Session 3)
    • MCP tools are also tools but are not Core Tools. They appear in the loop and are covered in Session 3.
    • Official descriptions (verbatim, source):
      • Skill: "Executes a skill within the main conversation"
      • Bash: "Executes shell commands in your environment"
      • Read: "Reads the contents of files"
      • Edit: "Makes targeted edits to specific files"
      • Write: "Creates or overwrites files"
      • Glob: "Finds files based on pattern matching"
      • Grep: "Searches for patterns in file contents"
      • Agent: "Spawns a subagent with its own context window to handle a task"
  • Memory
    • RiskMind uses the Claude Agent SDK's own memory: each chat is one jsonl file
    • There is no cross-conversation memory
  • Walking through the animation
    • Each turn is one step: the model decides, calls a tool, the result is appended to context, and the next turn starts. The Context panel grows with every turn, so the audience sees what enters context.
    • A scheduled run is identical to a normal chat: a new chat is opened, and the only difference is that the prompt is generated in the background instead of typed by a user
    • Turn 7 is a business skill calling another skill (render_html); this comes back in Session 3
    • The agent decides the next step each turn, but the order of the steps is defined by the skill

Agent Harness

Static infographic
On the slide
  • Harness = everything around the LLM that turns a model into an agent
To explain
  • Rule of thumb: everything except the LLM is the harness. In RiskMind the harness is the Claude Agent SDK, which is why the layer is labeled that way.
  • The picture: four layers drawn as half circles, from the inside out: LLM, Agent Harness, RiskMind Customization, Plugin. This slide highlights the Harness layer only. The same picture comes back on the next slides with a different layer highlighted: Customization on the next slide, and Plugin in Session 3.
  • What the harness provides: the ten mechanisms in the box. These are mechanisms only; what we put into them comes on the next slide.
    • Agent Loop, Core Tools and Memory / session were introduced on the Agent Introduction slide
    • Hooks and System prompt are mechanisms here. Our own hooks and our CLAUDE.md are Customization, on the next slide.
  • Why the harness matters
    • Same model, different harness, different agent
    • The model decides; the harness makes the decision executable, safe, and repeatable
    • Most of what we rely on in production (tool execution, session handling, permissions) is in the harness, not in the prompt
  • Key point to land: the harness is the part that is not specific to risk. Everything specific to RiskMind is added on top of it, which is the next slide.

  • The slide should stay consistent if Claude Agent SDK is replaced later; keep SDK-specific naming to a minimum

RiskMind Customization on Agent Harness

Static infographic
On the slide
  • The harness gives us the mechanisms; Customization is what we put in them
  • No custom tools: all Core Tools come from the Claude Agent SDK; business capability comes from skills and MCP
To explain
  • The picture: the same layers as the previous slide, now with the Customization layer highlighted. The box lists the three things we add.
  • CLAUDE.md: our custom system prompt for RiskMind
    • CLAUDE.md: "instructions you write to give Claude persistent context" (source)
    • Claude treats it as context, not as enforcement: "Claude treats them as context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead." (source)
  • Hooks: human in the loop. Bash execution needs the user's approval before it runs.
    • It is a PreToolUse hook with a Bash matcher
    • Hooks: "Hooks are user-defined shell commands. Claude Code runs them at specific points in its lifecycle, which gives you deterministic control: certain actions always happen rather than relying on the LLM to choose to run them." (source)
    • PreToolUse: "Before a tool call executes. Can block it" (source)
    • Matchers: "Without a matcher, a hook fires on every occurrence of its event. Matchers let you narrow that down." (source) Ours is Bash, so the approval applies to Bash only.
    • Why a hook and not the model: an approval that must always happen cannot be left to the LLM or to a prompt. Anything that must be exact is done in code, not by the LLM.
  • Skill: render_html
    • Almost every plugin needs it, so it sits in this layer and not inside any one plugin
    • Combines each section's comment and figure into the HTML report
  • No custom tools: all Core Tools come from the Claude Agent SDK. Business capability comes from skills and MCP.
  • Scope: this slide covers customization of the agent harness only. Backend and frontend implementation are a different layer and are not listed here.
  • Next: the Plugin layer and why we decouple the agent from the plugin
Notes (not on the slide)
  • The closing message about decoupling (Agent and Plugin are decoupled) is on the next slide, Why Agent + Plugin, and not here.

Why Agent + PluginDecoupling

Static comparison
On the slide
  • Core principle: business knowledge and the LLM-related process must be decoupled
  • The Agent and the Plugin are decoupled
    • Adding plugins does not change the three inner layers
    • Changing the agent does not affect plugins
    • A Local Risk Manager only needs to know how a plugin works

Add a new metricNew nodes in each product's graphNew tools for each productA new skill folder in each product's plugin
To explain
  • Why this slide: the earlier slides showed what RiskMind is built from. This one explains why we chose Agent + Plugin, given that we expect to keep adding products and metrics (the Expansion slide). It compares against the two other ways we could have built it.
  • Core principle: otherwise every business knowledge update touches the workflow, and every new platform feature touches the business knowledge
    • Changing the agent does not affect plugins: upgrade the Claude Agent SDK, or even stop using it one day, and plugins are unaffected
    • During expansion, a Local Risk Manager never has to touch anything on the Agent side
  • The two alternatives
    • Workflow (graph-based): defined on the AI Tools Landscape slide, predefined code paths, with every step a node and every transition an edge
    • Agent + Tools (all processes as tools): still an agent loop, so it handles exceptions itself, but there are no skills. Each step of the process is a custom tool (a Python function), and the whole process is described in a natural-language prompt. Each product is its own ReAct flow with its own prompt and its own tools. The user picks the product, and the system loads that product's prompt and tools. The agent cannot load anything by itself.
    • Agent + Plugin: the agent keeps a small set of general Core Tools, and business knowledge lives in skills. The agent sees each skill's name and description, picks what it needs, and loads it on demand.
    • Official description of the difference between custom tools and skills: "To add custom tools, connect an MCP server. To extend Claude with reusable prompt-based workflows, write a skill, which runs through the existing Skill tool rather than adding a new tool entry." (source)
  • Who builds it
    • A skill describes the process in natural language, and the exact steps are plain, independent Python scripts. A workflow also needs the orchestration written as code (graph, nodes, edges), and all processes as tools needs developers to write the tools.
    • Skills can be read and reviewed by risk colleagues, evaluated as a unit (AutoEval), and generated through conversation (AutoSkill)
  • How it grows
    • A new analysis, or even a single ad-hoc analysis, is a new skill folder. A workflow needs a new graph each time.
    • A small process change is an edit in the skill. In a workflow it can ripple across code.
    • Skills ship as plugins as content, so a skill change needs no code release
  • How it is managed
    • Skills use progressive disclosure. A router plus many workflows becomes hard to manage as workflows multiply.
    • Scripts stay independent files inside the skill. A workflow forces each one to be wrapped as a node.
    • A skill is a folder, so access can be managed with folder access
  • How it behaves
    • Drill-down and ad-hoc are natural language in chat, with follow-ups, and stay in one context
    • Exceptions (missing parameter, script error, unexpected data) are handled by the agent. A workflow needs an explicit node and edge for each case.
  • Where determinism lives: all data-critical steps are scripts. The agent orders and triggers them, and only the comments are LLM-generated.
  • Key message: the difference is who decides what gets loaded, and where business knowledge lives. With all processes as tools, the user and the system decide, and the knowledge sits in the agent's code. With Agent + Plugin, the agent decides, and the knowledge sits in the plugin.
