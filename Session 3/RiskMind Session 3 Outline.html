How Plugins, Skills, and MCP extend the agent.

Through-line · the question Sessions 1 and 2 left open

Why is RiskMind built as Agent + Plugin? Session 1 said RiskMind is Agent + Plugin. Session 2 compared the agent with RBC Assist Pro's augmented LLM and showed half of the context answer in the run, but never said why we chose this design. Session 2's preview hands over the other half: "how much effort does it take to add a new analysis?" (the second question from its beat 3). Session 3 opens with the question, answers it slide by slide, and closes with the answer.

  • Expansion A new analysis is a skill, a script and a query entry. A Risk Manager doesn't need to know how the agent works, how tools are registered, or how an MCP server is developed and hosted. The agent (AI runtime) and the plugins (business knowledge) are separate. RBC Assist Pro separates them too, but through MCP and without skills.
  • Context Download links keep the data out of the context (RBC Assist Pro has no such mechanism, so all data enters the context). Skills load only when used, so no MCP server has to be switched off by hand to cut the tool list (Session 2, beat 4). Progressive disclosure is designed for exactly this.

Each slide carries the tag(s) of the reason it supports.

Plugin Introduction

Static infographic with a short zoom-in. Zoom from the lit outer ring into the plugins folder: three real plugins, then one skill opens. The three things a Risk Manager writes appear last, with where each one lives.

Official definitions (verbatim, with sources)
  • In the Agent SDK: “Through the Agent SDK, you can programmatically load plugins from local directories to add capabilities to your agent sessions. A plugin can include: Skills … Agents … Hooks … MCP servers” Agent SDK, Plugins in the SDK
  • Plugin structure: .mcp.json holds the “MCP server definitions”. Agent SDK, Plugin structure reference
  • Same definition as Session 2's Business Plugin card (“… that the Claude Agent SDK loads as one unit”). The first sentence of the SDK page mentions Claude Code, so don't quote it.
Bullets
  • Why we introduce plugins: Risk Managers work on the plugin side, and all business knowledge reaches the agent through plugins
  • What is in a RiskMind plugin
    • One plugin per product: FX Option, Muni, IG Canada
    • One skill per analysis inside it (today Stress P&L; VaR and What-if Analysis next, as in Session 1's "Expand to More Analyses")
    • MCP configuration (.mcp.json): only the address of the MCP Gateway. The gateway routes each call and checks access, so a plugin never holds database details.
  • What a Risk Manager writes, and where it lives
    • SKILL.md: the analysis in plain English (in the plugin)
    • Scripts: the calculation, as command-line tools (in the plugin, inside the skill)
    • Query catalog entries: which data the analysis needs (in the data server's catalog, not in the plugin; Risk Managers add these themselves going forward)
  • Plugin and agent are decoupled (a short reminder; Session 2 covered it)
    • The agent is only pointed at the plugin folder. Adding or changing a plugin doesn't touch the agent, so a Risk Manager only needs to know how a plugin works.
    • This is the AI runtime kept apart from the business knowledge
  • Why a plugin and not standalone skills
    • Distribution: all analyses of a product ship together as one unit
    • One picture: business knowledge (skills) and the way to the data (the gateway address) live in the same unit
  • What all plugins share is not copied into each one. It goes into the Shared Library (its own slide, later).

SKILL.mdWhat a Skill Says, and How the Agent Follows It

AnimationExpansionContext

Merges the old "Skill Introduction" and "Walk Through One Real Example". Left: the real fxo-stress-pnl SKILL.md, folded into its five parts. Right: Session 2's run as a row of turns (T1 to T11). Each part of SKILL.md lights up together with the turns it drives, so the audience sees the run from Session 2 again, this time from the skill's side.

Official definitions (verbatim, with sources)
  • Agent Skills: “organized folders of instructions, scripts, and resources that agents can discover and load dynamically to perform better at specific tasks” Anthropic Engineering, Equipping agents for the real world with Agent Skills
  • Preloading: “At startup, the agent pre-loads the name and description of every installed skill into its system prompt.” same source
  • Progressive disclosure: “Progressive disclosure is the core design principle that makes Agent Skills flexible and scalable.” same source (first time the name is used in the series)
Bullets
  • What a skill is: one analysis for one product (for example, FX Option Stress P&L), written by the Risk Manager as a SKILL.md plus its scripts
  • SKILL.md in five parts (the same skeleton in all three real skills)
    • Description: what the skill is and when to use it. Real example: use it whenever the user asks about FXO stress, stress P&L, stress explain, or a spot/vol grid.
    • Business Background: what a careful new analyst needs to know. The two dates, the highlight scenario, raw versus display scenario names, BAU = GMRM + Murex add-on, and the Murex cross-check (a gap above $20MM is flagged as a data error).
    • Wording: how to say things. Currency pairs as USD/CAD, "stress profit increase" or "stress loss decrease", never "day-over-day".
    • Analysis Steps, the same five for every flow: fetch the data through MCP, run the analysis script, write the commentary, build the figures, render the report
    • Flows: the ways the skill is used. Portfolio Analysis, Detail Analysis, and Ad-hoc (in FXO, BAU Investigation). Each flow gives its slash command, its queries, its script command, the sections of the analysis file, and a template for the commentary with instructions for every field.
  • Each flow also decides what the user gets back: a dashboard (most flows), a card the script builds by itself with no commentary (Muni Trade Analysis), or a short answer in chat (Muni Implied Shock)
  • The rule in every skill: the numbers come from the scripts, not from the LLM. The LLM reads the summary the script writes and writes the words.

Context, in three levels
The description is always in the context. The body comes in only when the skill is used. The scripts are run, never read: only their output files' locations come back. That is progressive disclosure, and it is why the agent can know every skill without carrying all of them.
Open item
The real skill folder also has an IMPLEMENTATION.md (technical notes for developers); not shown unless we decide otherwise. FXO's BAU Investigation still uses its own fetch script (fetch_bau_data.py); not shown.

ScriptsTurning an Analysis into a Command

Static infographicExpansionContext

Before and after, side by side. Left: a script the way many of us write it today, with the inputs as constants at the top that we edit before every run. Right: the same script as a command, with every input on the command line, and the exact command as it appears in SKILL.md. Then the checklist.

Official definitions (verbatim, with sources)
  • Code: “Skills can also include code for Claude to execute as tools at its discretion.” Anthropic Engineering, Equipping agents for the real world with Agent Skills
Before and after
# before: edit the constants, then run
DATE      = "2026-08-11"
PREV_DATE = "2026-08-10"
SCENARIO  = "GLOBALFINANCIALCRISISABS"
INPUT     = "C:/Users/…/muni_0811.csv"
# after: every input is an argument (real Muni command)
uv run ${CLAUDE_SKILL_DIR}/scripts/portfolio_analysis.py \
  --portfolio-url <link> --prev-portfolio-url <link> \
  --inventory-url <link> --prev-inventory-url <link> \
  --scenario <scenario> \
  --output-path ${TEMP_OUTPUT_DIR}/… \
  --json-output-path ${TEMP_OUTPUT_DIR}/…
Bullets
  • The agent can't open a file and change a constant. It can only run a command. So every analysis needs one entry script that works as a command, one per flow (Muni: portfolio_analysis.py, detail_analysis.py, trade_analysis.py, implied_shock_analysis.py, plus the figures scripts).
  • What a script needs before an agent can run it
    • Every input is a command-line argument. Nothing to edit inside the file.
    • The full command, with every argument, is written in SKILL.md, so the agent knows exactly what to type
    • It writes its results to files and prints where they are
    • Two outputs: a .md summary for the LLM to read, and a .json for the next script
    • No human steps: no prompts, no clicking, no opening Excel halfway
    • Helpful errors: if a desk or product isn't found, it lists the valid ones, so the agent can correct itself (Muni Detail does this)
    • No local paths: it uses the skill's own folder and the run's output folder, and runs with uv
    • It reads the data from the download links itself
    • It takes the raw names (scenario, desk) as input; the display names only appear in the output
  • Three contracts that must match
    • The sections SKILL.md describes = the sections the script writes in the .md
    • The column aliases in the query catalog (for example pnlValue, scenarioName) = the columns the script reads
    • The commentary keys in SKILL.md = the keys the figures script expects
The point
A command run through Bash takes the place of registering a new tool. A new analysis needs no new tool, no change to the MCP server, and no redeploy. And because the script reads the data and writes a short summary, the data never passes through the LLM.

What MCP IsA Standard Way to Give an Agent Tools

Static infographicExpansionContext

Start with a one-line recap of what a tool is (defined in Session 2, beat 3), and where the agent's tools come from. Then the common belief, "MCP is a data connection", corrected row by row. Then the two MCP servers RiskMind actually uses, side by side. End with the contrast to Session 2's beat 3: the same analyses built as MCP tools.

Official definitions (verbatim, with sources)
  • Specification: “The Model Context Protocol (MCP) allows servers to expose tools that can be invoked by language models.” and “Tools enable models to interact with external systems, such as querying databases, calling APIs, or performing computations.” MCP specification, Tools
  • Server concepts: “MCP servers are programs that expose specific capabilities to AI applications through standardized protocol interfaces.” Tools are “Functions that your LLM can actively call, and decides when to use them based on user requests.” modelcontextprotocol.io, Understanding MCP servers
  • Dropped: the Anthropic announcement's “systems where data lives” and “data sources” wording. It reinforces the misunderstanding this slide corrects.
First, what a tool is (recap from Session 2)

Something the LLM can ask for but can't do itself. Each tool has a name, a description and the inputs it takes. The LLM only asks; the system runs it, and the result comes back into the context.

Where the agent's tools come from, and what is not a tool
What it isWhere it comes from
Core ToolsSkill, Bash, Read, Edit, WriteBuilt into the SDK
MCP toolsget_query_data, emit_turn_outputOffered by an MCP server
A skillNot a tool. A set of instructions.Loaded by the Skill tool (Session 2's T1)
A scriptNot a tool. A command.Run by the Bash tool (Session 2's T3)

The Skill tool and a skill are easy to mix up: the tool is the one call that loads it; the skill is what gets loaded. MCP is just one of the two places tools come from.

Common belief → what it actually is
What people thinkWhat it actually is
MCP is a data connectionMCP is a standard way of giving an agent tools. Fetching data is one thing a tool can do.
MCP is only for dataemit_turn_output is an MCP tool that shows the dashboard in the chat panel. It has nothing to do with data.
MCP lets the agent into the databaseThe agent can only call the tools a server offers. Our data server offers two, and neither takes SQL.

Bullets
  • Bridge from Session 1: there we called it the "data connection", because that's what we use it for today. What MCP is, is a standard plug for tools.
  • MCP tools are called in the agent loop exactly like the Core Tools (Session 2's T2 and T10)
  • The two MCP servers in RiskMind
    • Built into the backend: emit_turn_output. It ships with RiskMind and is always available; it just reaches the agent through MCP.
    • The data server, ATOM MCP: get_query_data and list_queries. Skills only use get_query_data. Reached through the MCP Gateway, whose address is all a plugin holds.
  • The other way to build it: every analysis as its own MCP tool, as in Session 2's beat 3 (fxo_portfolio(date), fxo_drill_down(date, by), muni_adhoc …). That is how RBC Assist Pro works.
    • Expansion Every new analysis means developing, registering, hosting and deploying a tool
    • Context Every tool's definition sits in the context, used or not, and servers are switched off by hand to keep it small
    • RiskMind keeps MCP tools few and general, and puts the analyses in skills

MCP Gateway, Tools and the Query CatalogHow the Agent Reaches the Data

AnimationExpansionContext

Trace one real query end to end, left to right: SKILL.md → Agent → MCP Gateway → ATOM MCP server → query catalog → database, and back. Use GSP_MUNI_POSITIONS_STRESS (Muni Detail Analysis). Then a table of the layers, and one catalog entry redrawn with notes.

The trace
  1. SKILL.mdnames the query for the flow: GSP_MUNI_POSITIONS_STRESS, once per date
  2. Agentcalls get_query_data(query_name, date)
  3. MCP Gatewaychecks the user's AD groups. No match, the call stops here.
  4. ATOM MCP serverlooks the name up in the catalog and runs that query for that date
  5. Back to the agenta download link, the row count, any pending dates, a message. The script downloads through the gateway, which checks access again.

The query returns the whole grid for the desks; the script filters what it needs. The same links are reused across flows ("do not re-fetch").

The layers

Why a catalog and not text-to-SQL (AiXel's governance list)
  • Traceability: every number traces back to a reviewed script and a named query
  • Least privilege: the agent can only run queries someone added to the catalog
  • Entitlement-based access: the agent inherits the user's existing permissions, never broader ones
  • Reproducibility: the same skill with the same dates gives the same numbers
  • Auditability: SKILL.md and the catalog are plain text in version control. Every catalog change is a commit tied to a ticket, so "what data could the agent get, and since when?" has a written answer.
Left out on purpose
  • group_name in depth: grouped roughly by product, with some groups combined. Not covered.
  • list_queries: exists, but no skill uses it
  • Per-skill query filtering on the server: not implemented. The skill names the exact query instead.
  • Repository names, FastAPI/FastMCP, LDAP and config file names: too technical for the audience

Shared LibraryWhat the Three Skills Have in Common

Waiting for detailsExpansionContext

Comes after one complete skill has been taught. The three SKILL.md files side by side; the parts that are the same light up together and lift out into one place.

Bullets
  • What we found in all three skills: the purpose and period-over-period paragraph, the raw/display name rules, the date rules, the command signature, analysis steps 3 to 5, the order for choosing a scenario in Detail, and the commentary patterns
  • So we built a Shared Library: shared knowledge and shared code, packaged as one installable package
  • Where it lives: next to the plugins, but not read from there. It is installed into the agent's environment, and the skills use it from there.
  • How a skill uses the shared knowledge: one line in SKILL.md pulls it in when the skill loads. The agent sees one complete SKILL.md, with no extra turn to read another file (Session 2's T1 stays one call).
  • Write once, use everywhere: a fix to a shared rule reaches every product's skill
